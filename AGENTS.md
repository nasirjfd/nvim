# Repository guidance

- For this repository only, validate your changes, then commit and push them to `main` before reporting the work as complete. Commit only changes belonging to the task; do not include unrelated user work. Use a short, single-line commit message without agent attribution. If validation, commit, or push fails, report the blocker rather than claiming completion. Explicit user instructions not to commit or push take precedence.
- This is a Neovim configuration, not an application with a standalone test suite. The entry point is `init.lua`; `lua/core/init.lua` loads core setup, and `lua/plugins/*.lua` are lazy.nvim plugin specs imported by `lua/core/lazy.lua`.
- Plugin versions are recorded in `lazy-lock.json`. Keep it in sync when intentionally changing plugin versions/specs; inspect lockfile changes rather than reverting them as incidental noise.
- Lua formatting is configured by `stylua.toml` (2 spaces, 100-column width, double quotes preferred). Format changed Lua with `stylua <files>` when available.
- Tests: while working run `tests/run.sh --changed` (only the specs for the files changed since HEAD, in seconds); before committing run `tests/run.sh` (every spec in parallel workers, about a minute). Add a spec in `tests/specs/` for every feature or fix; wait on real state with `h.wait(...)`, not fixed `vim.wait(ms)` sleeps. A failed wait prints the editor's screen and messages: read it before re-running. Never push a failing suite: `.githooks/pre-push` runs it. On a machine or clone where `git config core.hooksPath` is not `.githooks`, run `git config core.hooksPath .githooks` before anything else (`tests/run.sh` also does it the first time it runs). Details: `CLAUDE.md`, "Automated tests".
- For focused validation, run `nvim --headless -u ./init.lua '+qa'` to catch startup/config errors; this may bootstrap or update plugins and needs Neovim plus network access on a fresh setup. Interactive `:checkhealth` is the broader runtime diagnostic.
- `lua/core/lazy.lua` may install `tree-sitter-cli` via Cargo on startup if absent, and runs a throttled silent `lazy.sync()` once daily. Startup can therefore trigger installs/network activity.
- System dependency: GNU FriBidi (`brew install fribidi`; `libfribidi0` on Linux). `lua/core/rtl.lua` loads it through LuaJIT FFI to draw right-to-left text (Persian, Arabic, Hebrew) in visual order. On a new machine, or when `tests/specs/57_rtl_text.lua` fails with "GNU FriBidi is not installed", install it before anything else. Without it the module does nothing except a one-time message when RTL text is shown. The module is display-only (ephemeral overlays, never on the cursor line, only buffers with `buftype == ""`); never make it change the buffer, options (`conceallevel`, `guicursor`), keymaps or the cursor: an earlier version that did broke typing and search in English.
- System dependency: ImageMagick + Ghostscript (`brew install imagemagick ghostscript`). Snacks' image viewer converts a PDF opened in Neovim into an image with them; without them it shows "Image Conversion Failed" instead (the buffer is kept unmodified by `lua/plugins/snacks.lua`, spec `tests/specs/69_image_viewer_failure.lua`, so quitting does not ask to save the PDF).
- `init.lua` enables `exrc`; project-local `.nvim.lua` files may execute when opening a project. Treat them as executable configuration and inspect before enabling trust.

## Machines stay in sync (rule)

The user works on this config from more than one machine; every machine must end up with the same setup. This repo is the only channel between them, so whatever one machine has, the repo must record.

- **At the start of every session**, before other work: `git pull --ff-only` (stop and ask if it cannot fast-forward), then run `machine/check.sh`. It is report-only; fix every `FIX:` line it prints (each says how), tell the user what you changed, and re-run it until it prints `in sync`. Paths that differ per machine: `NVIM_PLUGIN_SRC`, `SUPERNOVA_VENDOR` (see the top of the script); if a checkout is not at the default path, find it, or ask the user.
- **Whenever you set something up outside the repo** (install a tool, a Homebrew package or cask, change a file under `~/.config` or `~/Library`, `defaults write`, a project's `.nvim.lua`/`.ignore`, a database, a minimum app version, anything else another machine would also need), in the same turn:
  1. put the file or the steps in the repo (the config itself, `herdr/`, `local-projects/`, `ghostty/`, or a section here),
  2. add a check for it to `machine/check.sh` (expected state + a `FIX:` line saying how to get there),
  3. commit and push.
  Something only written in chat, or only done on one machine, is lost for the other one.
- **Removing something** works the same way: remove it here, and leave a check (and a short section like "gtab is retired" below) so the other machine's agent removes it too.
- **Plugins**: `lazy-lock.json` is the truth. Restore with `NVIM_CONFIG_TESTS=1 nvim --headless '+Lazy! restore' +qa`; without `NVIM_CONFIG_TESTS=1` the daily auto-sync starts in the same process, races the restore and can leave clones half checked out (it happened with kulala.nvim). The plugin source repo (`multi-repo-code-diff`) is pulled like this repo.
- When the two machines disagree (the check reports a local file newer than the repo's copy), the newer side wins only after you have looked at the diff; if it is not clear which is newer, ask the user.

## gtab is retired (removed 2026-11-23): clean it up on every machine

herdr (`herdr/`) replaces gtab. The include `config-file = ".../.config/gtab/ghostty-shortcut.conf"` (with its `# gtab managed include` comment) was removed from `ghostty/config`; never add it back. On a machine where gtab is still around, when you start working there, tell the user and remove it:

- Ghostty configs outside this repo (`~/.config/ghostty/config`, a `config.ghostty` that is not the symlink to `ghostty/config`, `~/Library/Application Support/com.mitchellh.ghostty/config`): delete any gtab include line. If gtab wrote it back into `ghostty/config`, delete it there too and commit.
- gtab itself: find how it was installed (`command -v gtab`, `brew list | grep -i gtab`, `~/Library/LaunchAgents/*gtab*`) and uninstall it the same way, then remove `~/.config/gtab`. Ask the user first if anything there looks like their own data rather than gtab's generated files.
- Reload Ghostty (Cmd+Shift+,) afterwards.

## Related projects and real-project testing

- Reports of Git conflicts, missing changes, or broken merge UI in Supernova are requests to fix the Neovim/Git-pane tooling, not to resolve application conflicts. Never edit, stage, commit, merge, abort, reset, or otherwise change Supernova repositories for these tasks unless the user explicitly asks for that project operation. Use read-only inspection for real-project validation and isolated repositories for tests that need file changes or conflicts.
- Requests to change the Git pane may require edits in the separate source repository `~/Can/Develop/nvim/multi-repo-code-diff` (`https://github.com/nasirjfd/multi-repo-code-diff`). Read that repository's own agent guidance before editing it. Do not confuse it with Lazy's installed copy at `~/.local/share/nvim/lazy/multi-repo-code-diff`; make source changes in the source checkout, not the installed copy.
- For changes to that fork: validate, commit and push the source changes; update the installed plugin through Lazy (`:Lazy update multi-repo-code-diff`); verify the installed commit and test in Neovim; then commit and push this config repository's updated `lazy-lock.json` and any related config changes before reporting completion. Do not include unrelated work or force-push. Report any blocker instead of claiming completion.
- In testing/performance discussions, "the project" means `~/Can/Develop/php/supernova-env-dev/vendor` (on the current machine, `/Users/nasirjd/Can/Develop/php/supernova-env-dev/vendor`), not the plugin source or a temporary fixture.
- Normally use focused automated tests. When the user explicitly asks to "test on the project" or reports slowness/a problem "on the project", also reproduce and validate in that real working directory. Inspect its `.nvim.lua` before executing/trusting it; do not modify project files or run destructive operations merely to test the editor.
- These paths describe this machine's layout. On another machine, locate the corresponding checkouts; if unavailable, ask for their locations rather than silently substituting temporary fixtures. Guidance is repository-scoped, not a global rule for unrelated projects.
